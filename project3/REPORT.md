## 4. Как устроено решение

**A. Базовый уровень.** `errors.sh` — Bash-скрипт (shebang `#!/usr/bin/env bash`, все переменные в кавычках,
`set -euo pipefail`). Для каждого файла считает строки (`wc -l`) и ответы 5xx (`awk`), выводит итог и файл
с наибольшим числом 5xx. Результат: `results/A1_errors_output.txt`.

**B. Основной уровень.** `parallel_logs.py` создаёт N процессов через `os.fork`. Файлы раздаются по кругу
(`files[i::N]`). Каждый ребёнок разбирает свои файлы и пишет результат (JSON) в свою трубу `os.pipe`;
родитель читает трубы и склеивает результаты. Родитель закрывает конец для записи (иначе не будет «конца
данных»), а после чтения вызывает `os.waitpid` для каждого ребёнка — поэтому зомби не остаётся
(проверка `ps` встроена: ключ `--check-zombies`; результат — «ЗОМБИ НЕТ»).

**C. Продвинутый уровень.** `advanced.py` умеет возвращать результат тремя способами
(`--method pipe | shm | tmp`) — труба, `multiprocessing.shared_memory`, временные файлы.
Все три способа дают побайтно одинаковый отчёт (сверено по контрольной сумме).
Остановка по Ctrl+C: дети умирают по `SIGINT`, а родитель в блоке `finally` «хоронит» детей,
удаляет сегмент общей памяти и временную папку. `incident.py` находит начало и конец сбоев по строкам журнала.

## 5. Проверка Ctrl+C (задание C2)
`test_ctrl_c.sh` запускает `advanced.py` медленно, посылает `SIGINT` всей группе процессов (как терминал при
Ctrl+C) и проверяет остатки. Проверены все три способа и отдельно сигнал `SIGTERM` только родителю.
Во всех случаях: код выхода 130, процессов и зомби нет, в `/dev/shm` нет `psm_*`, в `/tmp` нет `logs_*`.
Полный вывод — `results/C2_ctrl_c_test.txt`.

При написании тест нашёл реальную ошибку: в способе `pipe` при Ctrl+C родитель пытался закрыть уже закрытую
трубу и падал, не «похоронив» детей. Исправлено: закрытие труб и сбор детей сделаны устойчивыми к ошибкам.
Также для `shared_memory` Python сам запускает служебный процесс `resource_tracker`; скрипт его останавливает,
чтобы после работы не оставалось процессов-сирот.

## 6. Измерения (компьютер с Windows + WSL, 8 ядер процессора)

Все замеры сняты командой `bash run_all.sh`; сырой вывод лежит в `results/`.

### 6.1. A2: `strace -c` для `wc -l` и для Python-подсчёта (файл `access_01.log`)

| | Всего системных вызовов | Три самых частых вызова |
|---|---:|---|
| `wc -l` | **138** | `mmap` — 27, `read` — 23, `openat` — 12 |
| `python3 count_one.py` | **515** | `read` — 139, `newfstatat` — 76, `rt_sigaction` — 66 |

Полные таблицы: `results/A2_strace_wc.txt`, `results/A2_strace_python.txt`.

**Чем объясняется разница.** Python делает почти в 4 раза больше системных вызовов (515 против 138).
- *Чтение файла.* У Python 139 вызовов `read` против 23 у `wc`. Файл около 835 КБ; Python читает его
  небольшими порциями (около 8 КБ), поэтому на сам файл уходит порядка сотни `read`. `wc` читает крупными блоками.
- *Запуск интерпретатора.* Python при старте обходит каталоги и открывает файлы модулей (`newfstatat` — 76,
  `openat` — 36, `getdents64` — 14) и настраивает обработчики сигналов (`rt_sigaction` — 66). Это и есть
  второй и третий по частоте вызовы у Python; у `wc` их почти нет.
- *У `wc` самый частый вызов `mmap` (27)* — это не чтение данных, а загрузка системных библиотек при запуске.
- Кроме системных вызовов, Python на каждую из 15 000 строк создаёт объект-строку, а `wc` лишь считает символы
  перевода строки; поэтому `wc` быстрее и по времени (в `strace`: 0,014 с против 0,025 с суммарно).

### 6.2. B: время при N = 1, 2, 4 процессах (`results/B_timing.txt`)

| N | запуск 1 | запуск 2 | запуск 3 | среднее | лучшее |
|---|---:|---:|---:|---:|---:|
| 1 | 2,538 с | 2,223 с | 2,152 с | **2,30 с** | 2,15 с |
| 2 | 1,396 с | 1,734 с | 2,335 с | **1,82 с** | 1,40 с |
| 4 | 1,212 с | 1,313 с | 1,061 с | **1,20 с** | 1,06 с |

С N = 4 процессами разбор примерно в 1,9–2 раза быстрее, чем с одним (по среднему 2,30 → 1,20 с; по лучшим
запускам 2,15 → 1,06 с). Ускорение есть, но не в 4 раза, потому что:
1. часть времени не делится между процессами: запуск Python, создание процессов (`fork`), пересылка и склейка результатов;
2. процессы упираются в чтение файлов с диска (файлы лежат на диске Windows и читаются через WSL, это медленнее,
   чем на обычном диске Linux) — это предположение, отдельно мы его не проверяли;
3. запуски заметно «шумят»: при N = 2 разброс от 1,40 до 2,34 с, поэтому сравнивать лучше средние и лучшие значения.

### 6.4. C1: три способа вернуть результат (N = 4)

| Способ | Время, с (3 запуска) | Среднее | Всего системных вызовов | Самые частые вызовы |
|---|---|---:|---:|---|
| pipe | 1,065 / 1,203 / 1,065 | **1,11 с** | **5 910** | `read` 4 367, `newfstatat` 441, `close` 194 |
| shm | 1,216 / 1,246 / 1,708 | **1,39 с** | **6 870** | `read` 4 474, `newfstatat` 704, `openat` 262 |
| tmp | 1,247 / 1,552 / 1,083 | **1,29 с** | **5 938** | `read` 4 365, `newfstatat` 442, `openat` 190 |

Файлы: `results/C1_timing.txt`, `results/C1_strace_pipe.txt`, `…_shm.txt`, `…_tmp.txt`.

**Что видно.**
- Во всех трёх способах доминирует `read` (около 4 400 вызовов): это дети читают 40 лог-файлов по 8 КБ.
  Передача результата (около 10 КБ на процесс) — малая часть работы, поэтому разница между способами небольшая.
- **pipe** — самый быстрый и с наименьшим числом вызовов. Специфичные вызовы: `pipe2` (4 трубы) и несколько `write`.
- **tmp** — на 28 вызовов больше, чем pipe: появляются `mkdir`, `rename` (4), `unlinkat` (4), `unlink`, `rmdir`
  — то есть работа с файловой системой и уборка за собой. Время чуть больше, чем у pipe.
- **shm** — самый «дорогой»: на 960 вызовов больше, чем pipe. Причина — служебный процесс `resource_tracker`,
  который Python запускает для `shared_memory` (отдельный интерпретатор: второй `execve`, `vfork`, `close_range`,
  сотни `newfstatat`/`openat`/`rt_sigaction`). Сами операции с памятью дёшевы (`ftruncate` — 1 вызов, `mmap`), но
  накладные расходы на служебный процесс и очистку (`unlink`) перекрывают выигрыш на таких малых данных.
- Строка `wait4` занимает около 70 % «времени» в таблицах `strace`: это родитель ждёт детей, а не работа;
  не стоит читать её как узкое место.
- Разница по времени (1,1 / 1,3 / 1,4 с) сопоставима с шумом между запусками (например, один запуск `shm` — 1,71 с),
  поэтому уверенно можно утверждать только порядок по числу системных вызовов: pipe ≈ tmp < shm.

**Вывод по способам.** Для небольших результатов проще и быстрее всего `pipe`. `shared_memory` оправдана при
больших объёмах данных, когда копирование через ядро становится дорогим. Временные файлы удобны, если результат
должен пережить процесс, но требуют аккуратной уборки.
